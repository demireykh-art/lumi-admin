**작성일**: 2026-08-15 · **상태**: 기획(구현 전) · **브랜치**: `claude/patient-app-qr-order-payment-njqis7`

## 0. 한 줄 결론

**기술적으로는 충분히 가능합니다.** 통합앱의 시술 수가표(`settings/feeSchedule`)가 이미
`procedures`(procId·이름·가격) 로 파생되고 있어서, 이 데이터를 그대로 환자용 메뉴로 쓸 수 있습니다.

다만 **식당 QR(오케이포스 tablepay) 모델을 그대로 옮기면 안 됩니다.**
식당은 "손님이 메뉴를 골라 주문 = 계약 성립"이지만, 의원은 **의사의 진료·상담이 선행되어야
시술이 확정**되고, 수납은 Vegas(전자차트)가 원천입니다. 그래서 두 단계로 나눠서 갑니다.

| 단계 | 무엇 | 식당 비유 |
| --- | --- | --- |
| **1단계 (권장 시작점)** | 실장이 상담에서 **확정한 오더**를 환자 폰으로 보내 결제 | "직원이 주문 받고 → 손님 폰으로 결제 링크" |
| **2단계 (확장)** | 환자가 QR로 메뉴를 **직접 열람·장바구니** → 상담 요청/결제 | "손님이 QR 찍고 직접 주문" |

---

## 1. 왜 식당형 셀프주문을 1단계로 하면 안 되는가

| 항목 | 식당 | 의원 |
| --- | --- | --- |
| 주문 주체 | 손님이 자유 선택 | 의사 진단 → 실장 상담 → **확정 오더** |
| 상품 확정성 | 메뉴=고정 | 부위·용량·마취·병용에 따라 가격 변동 |
| 사전 고지 | 없음 | **시술 동의서·부작용 설명** 필요 |
| 수납 원천 | POS | **Vegas** (의료비 자료 제출·수납 대장) |
| 잘못된 주문 | 취소·재조리 | 환불·분쟁, 경우에 따라 의료분쟁 |

환자가 자기 판단으로 "사각턱 보톡스 제오민"을 결제해버리면
① 진료 없이 시술이 판매된 모양이 되고, ② 실제 진료에서 다른 시술로 바뀌면 전부 환불 처리해야 하며,
③ 동의서 없는 선결제가 됩니다. 그래서 **결제는 항상 "확정 오더"에만 붙입니다.**

메뉴 열람·견적 확인은 자유롭게 열어도 무방합니다 (비급여 진료비용은 의료법상 오히려 고지 의무 대상).

## 2. 모델 3안 비교

### A안 — 완전 셀프주문형 (식당 그대로)
QR → 전체 메뉴 → 장바구니 → 결제 → 접수
- 장점: 데스크 수납 대기 제거, 가장 "요즘 방식"
- 단점: 위 1장의 리스크 전부. **비권장**

### B안 — 확정 오더 결제형 ✅ **권장 (Phase 1)**
상담(통합앱) → 실장이 오더 확정 → **[결제요청] 버튼** → 환자 폰에 QR/문자 링크 →
환자가 금액·항목 확인 → 카드/간편결제 → 결제완료가 통합앱 차트에 실시간 반영
- 장점: 기존 `visits.consultSection.confirmedOrders` 구조에 그대로 얹힘. 금액이 서버에서 확정됨.
- 단점: 환자가 스스로 여는 "메뉴판" 경험은 아직 없음

### C안 — 하이브리드 ✅ **최종 목표 (Phase 3)**
대기실 고정 QR(테이블 QR 역할) → 환자가 메뉴 열람 → 관심 시술을 **"상담 요청 장바구니"** 에 담음
→ 실장 화면에 뜸 → 상담 후 확정 → 결제는 B안 경로
- 식당의 QR 경험을 살리되, **장바구니 = 주문이 아니라 상담 희망 목록**
- 부가 효과: 환자가 뭘 보고 있는지 = 상담 리드 데이터

## 3. 아키텍처 — 지금 구조에서 무엇을 바꿔야 하나

### 3.1 가장 큰 제약: Firestore 규칙이 "로그인한 직원만"

```
// firestore.rules 현재
function signedIn() { return request.auth != null; }
match /{document=**} { allow read, write: if false; }
```

환자는 **비로그인**입니다. 그렇다고 규칙을 열면 안 됩니다(환자 차트·급여·매출이 같은 DB).

> **원칙: 환자앱은 Firestore에 직접 붙지 않는다. 전부 Cloud Functions 경유.**

```
[환자 폰]  patient.html (Vercel, 공개)
    │  fetch (HTTPS)
    ▼
[Cloud Functions]  publicMenu / createPaymentIntent / paymentWebhook
    │  Admin SDK (규칙 우회)
    ▼
[Firestore]  publicMenu · orderTokens · patientOrders · payments · visits
    ▲
    │  기존 경로 (로그인 직원)
[통합앱] staff.html
```

### 3.2 새 진입 파일

| 이름 | URL(예) | 파일 | 사용자 |
| --- | --- | --- | --- |
| 통합앱 | staff.lumiclinic.co.kr/staff.html | `staff.html` | 직원 |
| 관리자앱 | lumi-staff.vercel.app | `index.html` | 관리자 |
| **환자앱(신규)** | lumiclinic.co.kr/p 또는 `/patient.html` | `patient.html` | **환자(비로그인)** |

→ 구현 착수 시 `CLAUDE.md` 앱 이름 표에 "환자앱" 행 추가 필요.

### 3.3 데이터 모델(신규)

```javascript
// publicMenu/current  — 환자에게 보여줄 메뉴 스냅샷 (수가표에서 파생, 공개용 필터링)
{
  version: 12,
  publishedAt, publishedBy,
  categories: [{
    id, name,
    items: [{
      procId,            // = feeSchedule variant.id (기존 procedures 와 동일 키)
      name,              // "사각턱 보톡스 · 코어톡스"
      priceKRW: 100000,  // 원 단위 (VAT 정책 확정 후 표기)
      vatIncluded: true,
      desc, durationMin, imageUrl,
      publicVisible: true    // ← 통합앱 수가표에서 체크박스로 제어
    }]
  }]
}

// orderTokens/{token}  — QR/링크 1건 (서명된 짧은 코드)
{
  kind: 'order' | 'lobby',      // order=결제용 1회성, lobby=대기실 메뉴열람용 상시
  visitId, chartNo,              // order 일 때만
  amountKRW,                     // 서버가 확정한 청구액 (클라 신뢰 금지)
  items: [{procId, name, priceKRW, qty}],
  status: 'issued'|'opened'|'paid'|'expired'|'cancelled',
  expiresAt,                     // 발급 후 30분
  createdBy, createdAt
}

// patientOrders/{orderId} — 환자가 담은 상담 희망 목록 (C안)
{ tokenId, items:[{procId,name,qty}], memo, phone4, status:'new'|'seen'|'converted', createdAt }

// payments/{paymentId} — 결제 원장
{
  tokenId, visitId, chartNo,
  amountKRW, method:'card'|'kakaopay'|'naverpay'|'tosspay',
  pgProvider, pgTxId, pgRaw,
  status:'ready'|'paid'|'failed'|'cancelled'|'refunded',
  paidAt, cancelledAt, refundAmountKRW,
  vegasPosted: false,            // ← Vegas 수납 반영 여부 (중요, 아래 5장)
  vegasPostedBy, vegasPostedAt
}
```

기존 `visits.consultSection.confirmedOrders[].paymentStatus`(`unknown|pending|paid|refunded`)
와 `vegasPaymentRef` 필드가 이미 있으므로 **여기에 결제 결과를 되꽂으면 됩니다.**
회차권(`vouchers`)도 이미 있어 "회차권 구매 결제" 로 자연스럽게 확장됩니다.

### 3.4 Cloud Functions (신규 5개)

| 함수 | 타입 | 역할 |
| --- | --- | --- |
| `publishPublicMenu` | onCall(직원) | 수가표 → `publicMenu/current` 발행 (publicVisible 필터) |
| `getPublicMenu` | onRequest(공개) | 환자앱 메뉴 조회 (캐시 헤더, 읽기 전용) |

| `createPayment` | onRequest(공개) | PG 결제 준비 → 결제창 파라미터 반환 |
| `paymentWebhook` | onRequest(PG) | PG 웹훅 수신 → 서명검증 → `payments` 확정 → 차트 반영 |

## 4. 결제 수단 — 무엇을 붙일 것인가

| 옵션 | 내용 | 비고 |
| --- | --- | --- |
| **포트원(구 아임포트) V2** | 카드·카카오페이·네이버페이·토스페이 한 번에 | 통합 난이도 최저, 중개 수수료 소폭 |
| 토스페이먼츠 직연동 | 카드+간편결제, 문서 품질 좋음 | 직접 가맹 계약 |
| 나이스페이·KG이니시스 | 전통 PG | 계약·심사 다소 번거로움 |
| **현장 단말기 유지 + QR은 조회만** | 결제는 데스크 | 리스크 0, 효과도 0 |

권장: **포트원 V2로 시작** → 카드/카카오페이/네이버페이 동시 오픈, 추후 직연동 전환 가능.

전제 조건(원장님 확인 필요):
- 의료기관 사업자로 **PG 가맹 심사 통과** 필요 (업종코드 확인)
- 정산 주기 D+2~D+5, 수수료 대략 2.2~3.5%
- 환불(부분취소 포함) API 사용 → 통합앱에 환불 버튼 필요

## 5. ⚠️ 실무상 가장 큰 병목 — Vegas 수납 이중 입력

QR로 결제받은 돈은 **Vegas 수납 대장에 자동으로 잡히지 않습니다.** 그런데:

- 의료기관은 **연말정산 의료비 자료를 국세청에 제출**할 의무가 있고, 그 원천은 Vegas입니다.
- 현금영수증 의무발행 업종이며, 카드 결제분은 PG 매출로 잡힙니다.
- 매출 대사(`revenue/{ym}` 파싱)와 어긋나면 급여 인센티브 계산까지 틀어집니다.

**대응(택1, 원장님 결정 필요)**
1. **(권장·현실적)** 결제 완료 시 통합앱 차트에 `[Vegas 수납 미반영]` 빨간 배지 →
   데스크가 Vegas에 수납 입력 후 `vegasPosted` 체크. 미반영 건은 마감 화면에서 강제 노출.
2. Vegas API/DB 연동 자동화 — `docs/charting-v2.md` 비목표에 "실시간 Vegas API 연동 안 함"으로
   이미 결정되어 있음. 벤더 협의 필요.
3. QR 결제는 **회차권·선불권 판매에만** 한정 (당일 시술비는 기존 데스크 수납 유지) —
   대사 대상이 줄어 가장 안전한 시작.

> 이 항목이 정리되지 않으면 **결제 기능은 켜지 않는 것을 권합니다.** 기술이 아니라 회계 문제입니다.

### 6.1 지금 발견된 데이터 불일치 (결제 붙이기 전 반드시 해결)

- `treatments-seed.json` `_meta.vat` = **"별도"**
- `staff.html` `_deriveProceduresFromFee()` = `vatIncluded: **true**` (포함으로 하드코딩)

수가표의 `4`(=40,000원)가 VAT 포함인지 별도인지에 따라 **환자가 실제로 낼 금액이 10% 달라집니다.**
메뉴 공개·결제 전에 정책을 확정하고 한쪽으로 통일해야 합니다.

## 7. 화면 흐름

### 환자앱 (`patient.html`)
```
[QR 스캔]
   ├─ lobby 토큰 → ① 메뉴 홈 (카테고리 탭 · 가격 · 설명)
   │                   → ② 상세/장바구니("상담 시 문의하기") → ③ 상담요청 전송(뒤4자리)
   └─ order 토큰 → ④ 결제 확인서 (항목·금액·주의사항·환불규정 동의)

```
- 디자인: 통합앱과 동일 톤, 모바일 전용, 로그인 없음, 하단 고정 CTA
- 접근성: 큰 글씨 모드(중장년 환자 비중)

### 통합앱 (`staff.html`) 추가분
- 상담 차팅 실장 탭 확정 오더 옆 **[💳 결제요청]** → QR 모달 + 문자 발송
- 결제 상태 실시간 배지 (`미결제 → 결제중 → 결제완료 → Vegas 미반영`)
- 수가표 각 옵션에 **[환자 공개]** 체크 + 상단 **[메뉴 발행]** 버튼
- 새 홈 카드 **📱 환자앱 주문** (상담요청 인박스 + 결제 내역 + 환불)

## 8. 보안 설계 (공개 엔드포인트가 생기므로 필수)

1. **금액은 절대 클라이언트에서 받지 않는다** — 토큰 → 서버가 `amountKRW` 확정.
2. 토큰은 예측 불가(32자 랜덤) + **30분 만료** + 1회 결제 후 즉시 `paid` 잠금.
3. 웹훅 **서명 검증 + 멱등키**(같은 `pgTxId` 중복 처리 금지).
4. 결제 성공 판정은 **웹훅/서버 조회 결과만 신뢰** (브라우저 리다이렉트 신뢰 금지).
5. 공개 엔드포인트 **레이트리밋**(IP·토큰별), 차트번호·환자명은 응답에 넣지 않음.
6. `publicMenu`는 **공개 전용 사본** — 원가·레시피·태그 등 내부 필드 제거.
7. Firestore 규칙: 신규 컬렉션은 **직원 읽기만** 허용, 환자 경로는 열지 않음(전부 Functions).
