## 0. 한 줄 결론

**바로 만들 수 있습니다.** 참고한 식당(몬자상)도 **주문은 QR 사이트, 결제는 데스크**입니다.
이 구조를 그대로 가져오면 온라인 결제(PG·환불·선결제·Vegas 이중입력) 이슈가 **전부 사라집니다.**

남는 것은 순수한 기능 세 가지뿐입니다.

1. **메뉴 열람** — 우리 시술에 뭐가 있고 얼마인지 환자가 직접 본다
2. **담기** — 관심 있는 시술을 담아두고 상담 때 꺼낸다
3. **추가 시술 유도** — 담는 과정에서 자연스럽게 더 보게 만든다

그리고 결정적으로, **이 세 가지에 필요한 데이터가 이미 통합앱 안에 다 있습니다.**

| 필요한 것 | 이미 있는 것 | 위치 |
| --- | --- | --- |
| 메뉴(시술·옵션·가격) | `settings/feeSchedule` → `procedures` 파생 | `staff.html:7126` `_deriveProceduresFromFee()` |
| 고민별 탐색 경로 | `settings/consultTree` (고민→시술→오더 3~5단계) | `staff.html:7955` `CONSULT_SEED_V3` |
| 시술 성격 태그 | `CONSULT_TAGS` (피부·쳐짐·꺼짐·전문) | `staff.html:7415` |
| 담긴 것 → 실제 오더 | `visits.consultSection.confirmedOrders` | `docs/charting-v2.md` |
| 회차권 | `vouchers` 컬렉션 | `staff.html:3026` |

**새로 만들 것은 환자용 화면(`patient.html`)과 그 앞의 얇은 서버 한 겹뿐입니다.**

## 1. 식당 모델 그대로 옮기기

| 식당 (몬자상) | 루미의원 |
| --- | --- |
| 테이블 QR 스티커 | **상담실·대기실 QR 스탠드** |
| "테이블 R2" | "상담실 2" / 대기 번호 코드 |
| 메뉴 탭 (세트/철판류/토핑류) | 수가표 카테고리 (보톡스/필러/레이저…) |
| 담기(+) → 주문 | 담기(+) → **상담 요청 목록** |
| 직원이 주문 확인 | **실장이 상담에서 확인·확정** |
| 데스크에서 결제 | **데스크에서 Vegas 수납** (기존 그대로) |
| 리뷰 이벤트 배너 | ⛔ **넣지 않음** (의료법 §27 환자 유인 소지) |

### 딱 하나 다르게 가야 하는 것: "담기 ≠ 주문"

식당은 담으면 주방으로 갑니다. 의원은 담아도 **시술이 확정되지 않습니다.**
부위·용량·피부 상태에 따라 원장 판단이 필요하기 때문입니다. 그래서 버튼 문구를
"장바구니"가 아니라 이렇게 씁니다.

> **[＋ 상담 때 물어볼래요]**

이 한 줄이 ① 결제가 아님을 분명히 하고, ② 담는 심리적 부담을 없애고(= 더 많이 담음),
③ "확정은 상담에서"라는 절차를 자연스럽게 만듭니다. 결과적으로 **업셀에도 더 유리합니다.**

## 2. 누가 담았는지 어떻게 아나 (= 식당의 "테이블 번호")

식당은 테이블 번호로 손님을 식별합니다. 의원은 세 가지 방법이 있습니다.

| 방식 | 식별 | 장점 | 단점 |
| --- | --- | --- | --- |
| **(A) 상담실 고정 QR** | "상담실 2" | 실장이 지금 누가 앉았는지 앎. 식당과 완전 동일 | 상담실 밖(대기실)에선 못 씀 |
| **(B) 익명 대기실 QR + 코드** | 6자리 코드 화면 제시 | 개인정보 0. 대기 시간 활용 극대화 | 환자가 코드를 보여줘야 함 |
| **(C) 접수 시 1회용 QR 발급** | 차트번호 직결 | 가장 정확, 차트 자동 연결 | 데스크 업무 1스텝 추가 |

**권장: (A) + (B) 로 시작.** 둘 다 개인정보를 전혀 받지 않아 바로 시작할 수 있습니다.
(C)는 운영이 익숙해진 뒤 Phase 3에서 붙입니다.

(B)의 코드 제시 방식은 식당 예시의 "작성 완료 화면을 직원에게 보여주시면"과 정확히 같은 UX입니다.

## 3. 🎯 추가 시술 유도 (업셀) — 이번 기획의 핵심

식당 메뉴판은 "토핑류"로 객단가를 올립니다. 우리는 여섯 가지 장치를 씁니다.
**중요한 것은 위 4개가 이미 있는 데이터로 지금 만들 수 있다는 점입니다.**

### ① 고민별 탐색 — `consultTree` 재사용 ⭐ 가장 강력

수가표 축(보톡스/필러…)은 **이미 뭘 받을지 아는 사람**만 찾습니다.
반면 `CONSULT_SEED_V3`는 이렇게 생겼습니다.

```
피부퀄리티 > 톤 > 칙칙함 > BBL > BB토닝 > 1회 30만원 / 5회 120만원
피부퀄리티 > 색소 > 흑자 > 리팟 > 5mm 기준 30만원
```

**환자의 언어("얼굴이 칙칙해요")로 시작해서 시술과 가격으로 끝납니다.**
이걸 환자앱 첫 화면에 그대로 깔면, 환자가 스스로 "내 고민 → 해결 시술"을 찾아옵니다.
실장이 상담에서 하던 탐색을 **대기 시간에 환자가 미리 하고 오는 것**이라 전환율이 높습니다.

> 메뉴 탭 구성: **[고민별로 찾기]** (기본) · [시술별로 보기] · [회차권]

### ② 회차권 비교 카드 — 객단가 직접 상승

트리에 이미 `1회 30만원` / `5회 120만원` 이 나란히 있습니다. 이걸 표로 보여줍니다.

```
BB토닝   1회  300,000원
        5회  1,200,000원   ← 1회당 240,000원 (20% 절약)
```

단건을 보러 온 환자에게 회차권을 노출하는 것만으로 객단가가 올라갑니다.
확정 시 기존 `vouchers` 컬렉션으로 그대로 이어집니다.

### ③ 함께 많이 받는 시술 — `visits` 이력 기반 자동 추천

`confirmedOrders[].procId` 가 쌓여 있으므로 **동시 선택 빈도(co-occurrence)** 를 계산할 수 있습니다.

> "보톡스를 받으신 분들이 함께 많이 받은 시술" → 리쥬란 · LDM재생관리

데이터가 쌓일수록 정확해집니다. 초기엔 ④로 대체합니다.

### ④ 실장 큐레이션 추천 — `settings/patientMenu` (초기 기본값)

자동 추천 데이터가 쌓이기 전에는 **실장이 직접 "이 시술 옆엔 이걸 붙인다"를 지정**합니다.
통제 가능해서 의료광고 리스크도 없고, 현장 감각이 그대로 반영됩니다.

```javascript
recommendMap: { '<procId:보톡스>': ['<procId:리쥬란>', '<procId:LDM재생관리>'] }
```

### ⑤ 애드온(토핑) — 마취연고·재생관리

`ANESTHESIA_SEED`(리도카인 크림·EMLA…)와 LDM재생관리처럼 **본 시술에 붙는 항목**을
식당의 "토핑류"처럼 별도 섹션으로 노출합니다.

### ⑥ 담긴 목록 실시간 알림 — 전환의 마지막 한 걸음 ⭐

환자가 담는 즉시 **실장 화면에 뜹니다.** 상담 시작 시 실장이 이미 알고 있습니다.

> "리쥬란 보고 계셨네요, 지금 피부결이면 같이 하시면 좋아요"

**이게 실제 매출로 바뀌는 지점입니다.** 자동 추천보다 이 한 줄이 훨씬 강력합니다.

### ⚠️ 업셀에서 하면 안 되는 것

| 금지 | 이유 |
| --- | --- |
| "이벤트 · 최저가 · 1+1 · 오늘만" | 의료광고 심의 대상 (의료법 §56) |
| 리뷰 작성 시 시술·물품 제공 | **환자 유인·알선 (의료법 §27)** — 식당 예시의 리뷰 이벤트가 여기 해당 |
| 할인율 강조 배너 | 위와 동일 |
| 자동 "지금 결제" 유도 | 진료 없는 판매가 됨 |

→ **가격은 정가 그대로 표시.** 회차권 단가 비교(②)는 할인 광고가 아니라 **가격 고지**라 안전합니다.
비급여 진료비용 게시는 의료법 §45상 오히려 **의무**입니다.

## 4. 아키텍처

### 4.1 제약: Firestore 규칙이 "로그인한 직원만"

```
// firestore.rules 현재
function signedIn() { return request.auth != null; }
match /{document=**} { allow read, write: if false; }
```

환자는 비로그인입니다. 그렇다고 규칙을 열 수 없습니다 — 같은 DB에 환자 차트·급여·매출이 있습니다.

> **원칙: 환자앱은 Firestore에 직접 붙지 않는다. 전부 Cloud Functions 경유.**

```
[환자 폰]  patient.html  (Vercel, 공개, 로그인 없음)
    │  fetch (HTTPS)
    ▼
[Cloud Functions]  getPatientMenu · openSession · addToCart
    │  Admin SDK
    ▼
[Firestore]  patientMenu · menuSessions   ←→   기존 visits · vouchers
    ▲
    │  (로그인 직원)
[통합앱] staff.html — 담긴 목록 확인 · 오더 확정 · 데스크 수납
```

결제가 없으므로 **PG·웹훅·환불 API가 전부 불필요**합니다. 서버가 매우 얇아집니다.

### 4.2 새 진입 파일

| 이름 | URL(예) | 파일 | 사용자 |
| --- | --- | --- | --- |
| 통합앱 | staff.lumiclinic.co.kr/staff.html | `staff.html` | 직원 |
| 관리자앱 | lumi-staff.vercel.app | `index.html` | 관리자 |
| **환자앱(신규)** | lumiclinic.co.kr/m 또는 `/patient.html` | `patient.html` | **환자(비로그인)** |

→ 착수 시 `CLAUDE.md` 앱 이름 표에 "환자앱" 행 추가.

### 4.3 데이터 모델

```javascript
// patientMenu/current — 환자 공개용 메뉴 스냅샷 (수가표+상담트리에서 발행)
{
  version: 3, publishedAt, publishedBy,
  byCategory: [{                    // 시술별로 보기 (수가표 축)
    id, name,
    items: [{ procId, name, priceKRW, desc, durationMin, imageUrl, tags:['skin'] }]
  }],
  byConcern: { ... },               // 고민별로 찾기 (consultTree 축, leaf 에 procId 매핑)
  vouchers: [{ procId, name, sessions:5, priceKRW, unitPriceKRW }],  // 회차권 비교용
  addons:   [{ procId, name, priceKRW }],                            // 마취·재생관리 등
  recommendMap: { procId: [procId, ...] }                            // ④ 큐레이션 추천
}
// ※ 원가·레시피·재고·내부 메모는 절대 포함하지 않음 (공개 전용 사본)

// menuSessions/{sessionId} — 식당의 "테이블 오픈"에 해당
{
  kind: 'room' | 'lobby',
  roomLabel: '상담실 2',            // kind='room'
  showCode: '4821',                 // kind='lobby' — 환자가 직원에게 보여주는 코드
  cart: [{ procId, name, priceKRW, qty, addedAt }],
  viewed: [{ procId, at }],         // 담지 않고 본 것 — 상담 힌트로 활용
  memo: '',                         // 환자 자유 입력 (선택)
  status: 'open' | 'seen' | 'converted' | 'closed',
  visitId: null,                    // 실장이 차트와 연결하면 채워짐
  createdAt, expiresAt              // 당일 자정 만료
}
```

**`payments` 컬렉션은 만들지 않습니다.** 수납은 기존대로 Vegas가 원천입니다.

## 6. 보안·개인정보

결제가 없어 리스크는 크게 낮지만, **공개 엔드포인트가 처음 생기는 것**이므로 아래는 필수입니다.

1. **개인정보를 아예 받지 않는다** — 이름·전화·차트번호 입력란 없음. 세션은 익명 코드뿐.
2. 시술명은 **민감정보(건강정보)** — URL·QR에 시술명 노출 금지, 세션 토큰 뒤로만 조회.
3. 세션 토큰 32자 랜덤, **당일 자정 만료**, 세션당 담기 최대 30건(스팸 방지).
4. 공개 엔드포인트 레이트리밋(IP·세션별), 응답에 내부 필드(원가·레시피·재고) 절대 미포함.
5. `patientMenu`는 **공개 전용 사본** — `feeSchedule` 원본을 그대로 노출하지 않음.
6. Firestore 규칙: `patientMenu`·`menuSessions`는 **직원 읽기/쓰기만** 허용. 환자 경로는 열지 않음(전부 Functions).
7. 상담실 QR은 **다음 환자가 앉으면 세션 초기화** — 앞 환자가 본 내역이 남지 않게.

## 7. 남은 확인 사항 (결제가 빠져서 대폭 축소됨)

### 7.1 ✅ VAT 표기 — **부가세 10% 별도로 확정** (2026-08-15)

수가표 정가는 **VAT 별도**입니다(`treatments-seed.json` `_meta.vat="별도"` 기준).
코드에 `vatIncluded:true` 로 하드코딩되어 있던 불일치를 `false` 로 바로잡았습니다.

- `staff.html` `_deriveProceduresFromFee()` · 시술 마스터 upsert → `vatIncluded:false`
- 환자앱은 모든 금액을 **「시술 금액 / 부가세 10% / 결제 예상 금액」 3줄**로 표기
- 상단에 「표시 금액은 부가세(10%) 별도입니다」 상시 배너

예: 수가표 `4` → 시술 금액 40,000원 · 부가세 4,000원 · **결제 예상 44,000원**

### 7.2 Vegas 수납 — 이제 문제가 아니라 개선점

이전 기획(온라인 결제)에서는 QR 결제분이 Vegas에 안 잡혀 세무 리스크가 컸습니다.
**데스크 수납이면 기존 흐름 그대로**라 리스크가 0이고, 오히려 데스크가 담긴 목록을 보고
입력하므로 **수납 입력이 빨라집니다.**

### 7.3 의료법 체크

| 항목 | 판단 |
| --- | --- |
| 비급여 가격 게시 (§45) | **고지 의무 대상** — 메뉴 공개는 부합 ✅ |
| 의료광고 (§56) | 정가 표시는 안전. "이벤트·최저가·할인" 표기만 금지 ⚠️ |
| 환자 유인·알선 (§27) | 리뷰 이벤트류 **제외 확정** ⛔ |
| 시술 동의서 | 담기는 결제가 아니므로 기존 절차 그대로 ✅ |
| 개인정보 | 수집 자체를 안 함 ✅ |

## 11. Phase 1 구현 결과 (2026-08-15)

### 11.1 만들어진 것

| 파일 | 내용 |
| --- | --- |
| **`patient.html`** (신규) | 환자앱 — 로그인·개인정보·결제 없음. 고민별/시술별 탭, 검색, 큰 글씨 모드 |
| `functions/index.js` | **`getPatientMenu`** 추가 — 공개 엔드포인트(asia-northeast3). `patientMenu/current` 만 읽고, 화이트리스트한 필드만 응답 |
| `staff.html` | 수가표 상단바에 **📱 버튼** → 「환자앱 메뉴」 모달 (공개 선택 · 발행 · QR · 링크) |
| `staff.html` | `vatIncluded: true → false` (VAT 별도 확정) |
| `firestore.rules` | `patientMenu/{id}` 화이트리스트 (직원만 읽기·쓰기) |
| `vercel.json` (신규) | `/m` → `/patient.html` 리라이트 (QR 인쇄용 짧은 주소) |

### 11.2 운영 순서

1. 통합앱 → **시술 수가표** → 상단 **📱** 버튼
2. 공개할 시술을 체크 (카테고리별 [전체]/[해제], 검색 지원)
   → 공개 여부는 수가표 옵션의 `pub` 플래그로 저장되어 **다음에 열어도 유지**
3. (선택) **「고민별로 찾기」 탭 공개** 체크 — 상담 트리 기반 탐색
4. (선택) 상단 안내문구 입력
5. **[📤 발행하기]** → `patientMenu/current` 저장 → 환자앱 즉시 반영
6. 모달의 **QR·링크**를 인쇄해 대기실·상담실에 비치

> 수가표를 고쳐도 환자앱은 **발행을 눌러야 반영**됩니다. 가격을 바꾸면 다시 발행하세요.

### 11.3 안전장치

- **내부 표기 자동 차단** — 상담 트리의 `세부오더`·`회차별 프로그램 상세` 는 노드 이름이든
  잎이든 환자 화면에 노출되지 않고 **「상담 시 안내」**로 치환됨
- **가격 오표기 방지** — 고민별 트리의 항목은 ① 이름에 적힌 `○만원` 을 파싱하거나
  ② 공개 시술과 **이름이 정확히 같고 가격이 하나로 특정될 때만** 가격을 표시.
  애매하면 「상담 시 안내」 (예: 트리의 `보톡스` → 옵션별 가격이 달라 가격 미표시)
- **내부 정보 미발행** — 소모품·원가·분당수익·재고·태그 원본은 발행 payload에 포함되지 않음
- 환자앱에는 **결제·개인정보 입력이 없음** — 하단에 「상담 때 말씀해 주세요」 안내만

### 11.4 배포 시 필요한 것 ⚠️

1. **`main` 병합** → Vercel 자동 배포 (`patient.html`, `/m`)
2. **Firestore 규칙** — `main` 푸시 시 GitHub Actions 자동 배포
3. **Cloud Functions 수동 배포 필요**:
   ```
   cd functions && firebase deploy --only functions:getPatientMenu
   ```
   → **이 배포 전에는 환자앱이 메뉴를 불러오지 못합니다** (「메뉴를 준비 중입니다」 표시)
