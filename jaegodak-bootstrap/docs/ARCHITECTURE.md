# 재고닥 아키텍처 — 결정과 근거

이 문서는 **왜 이렇게 골랐는지**를 적어 둡니다. 나중에 "그때 왜 이렇게 했지"를
다시 논쟁하지 않기 위해서입니다.

---

## 1. 서버 — Firebase. AWS 는 지금이 아니다

### 1-1. 질문의 전제부터 바로잡습니다

> "처음에는 비용이 안 들게 개발하고 나중에 안정적인 서버를 이용한다?"

**Firebase 가 불안정한 게 아닙니다.** GCP 위에서 도는 관리형 서비스이고,
가용성·백업·확장은 구글이 책임집니다. 병원 100 곳 규모에서는 한계에 닿지도 않습니다.

**무료 → 유료는 서버를 바꾸는 일이 아니라 요금제를 바꾸는 일입니다.**
Spark(무료) → Blaze(종량제)는 콘솔에서 버튼 하나이고 코드가 바뀌지 않습니다.
그래서 "나중에 옮긴다"는 계획 자체가 필요 없습니다.

### 1-2. 진짜 리스크는 "나중에 옮기기" 입니다

Firestore(문서 모델) → RDS(관계형)는 **자동 변환이 안 됩니다.**
질의 방식, 트랜잭션 경계, 실시간 구독, 오프라인 캐시가 전부 다릅니다.
나중에 AWS 로 옮긴다는 건 "나중에"가 아니라 **제품을 다시 쓰는 일**입니다.

> **그러니 지금 고르는 것이 사실상 최종 결정입니다.** 그 전제로 골라야 합니다.

### 1-3. 그 전제에서도 Firebase 가 맞습니다

| | 근거 |
| --- | --- |
| **학습곡선 0** | 루미가 이미 Firebase 입니다. 이관 스크립트도 같은 SDK 로 양쪽을 붙입니다 |
| **조립할 게 없다** | Auth · DB · 실시간 · 오프라인 · 정적호스팅 · 서버리스가 한 묶음 |
| **오프라인이 공짜** | 병원 와이파이가 끊겨도 앱이 돕니다. 재고 앱에서 이건 기능입니다 |
| **1 인 개발** | 인프라에 쓰는 시간이 곧 제품에 못 쓰는 시간입니다 |

AWS 로 같은 것을 하려면 **Cognito + DynamoDB(또는 RDS) + Lambda + API Gateway
+ S3 + CloudFront + IAM** 을 직접 조립하고 계속 관리해야 합니다.
실시간 동기화와 오프라인 캐시는 그러고도 직접 만들어야 합니다.

### 1-4. 비용

| | Firebase |
| --- | --- |
| 요금제 | **Blaze(종량제) 필수** — Functions 가 외부 네트워크(비전 API)를 부르려면 |
| 무료 할당량 | Blaze 에서도 그대로 유지됩니다 |
| 파일럿(병원 2~3 곳) | **실질 0 원**. 무료 할당량 안에서 끝납니다 |
| 병원 100 곳 규모 | Firestore 읽기·쓰기 + Functions 호출 + 비전 LLM 이 합쳐져 **월 수만 원대** 예상 |

> ⚠️ 금액은 개략치입니다. 착수 시점 요금표로 다시 계산하십시오.
> **예산 알림을 월 1 만원으로 걸어 두는 것**을 권합니다 (GCP 콘솔 → 결제 → 예산).
> 종량제의 유일한 위험은 버그로 인한 폭주인데, 알림이 그것을 잡습니다.

### 1-5. AWS 로 갈 시점 — 미리 적어 둡니다

넷 중 하나라도 해당되면 그때 다시 검토합니다.

1. 병원 **500 곳 이상**
2. 복잡한 관계형 리포트가 제품의 핵심이 됨 (Firestore 가 제일 약한 지점)
3. 기업 고객이 **VPC · 온프레미스 · 특정 리전**을 계약 조건으로 요구
4. 인프라 비용이 **월 수백만 원**

지금은 넷 다 아닙니다.

### 1-6. 그래도 락인을 줄이는 장치 — P0 부터 넣었습니다

옮길 일이 없기를 바라지만, 옮겨야 할 때 **고칠 파일이 적도록** 만들어 둡니다.

| 장치 | 어디 | 효과 |
| --- | --- | --- |
| **데이터 접근을 한 계층으로** | `public/repo.js` | 화면 코드는 Firestore 를 모릅니다. 백엔드를 바꾸면 이 파일만 다시 씁니다 |
| **Rules 에 업무 규칙을 안 넣는다** | `firestore.rules` | Rules 가 답하는 질문은 하나뿐입니다 — "이 사람이 이 병원 사람인가". 재고 음수 금지 같은 것은 `repo.js` 가 막습니다 |
| **Functions 는 얇게** | `functions/index.js` | 지금은 테넌시만. 업무 로직이 서버리스에 쌓일수록 이식이 어려워집니다 |
| **export 를 상시 유지** | `scripts/` | 데이터를 언제든 JSON 으로 뽑을 수 있으면 인질이 아닙니다 |

## 2. 지역 — `asia-northeast3` (서울)

- 국내 병원 대상이라 지연시간이 가장 낮습니다.
- 루미와 같은 지역이라 이관 스크립트가 빠릅니다.
- **데이터가 국내에 있다**고 고객에게 말할 수 있습니다. 의료 쪽에서 이건 영업 자산입니다.

> ⚠️ **Firestore 위치는 생성 후 변경할 수 없습니다.** 프로젝트를 새로 만들어
> 데이터를 옮기는 것 말고는 방법이 없습니다.

## 3. 멀티테넌시 — 클레임 기반, 하위 컬렉션

### 3-1. 구조

```
clinics/{clinicId}/items/{itemId}
clinics/{clinicId}/movements/{movementId}
clinics/{clinicId}/members/{uid}
users/{uid}          ← 본인만
invites/{code}       ← 코드를 아는 것이 곧 권한
```

**병원 데이터는 `clinics/{clinicId}/` 아래에만 삽니다.** 최상위 컬렉션은 셋뿐입니다.

> 루미는 최상위 컬렉션이 31 개까지 자란 뒤에 멀티테넌시를 붙이려다 못 붙였습니다
> (`AUDIT.md`). 그래서 재고닥은 **처음부터 최상위를 잠가** 뒀습니다.
> Rules 마지막의 `match /{document=**} { allow read, write: if false; }` 가 그것입니다.

### 3-2. 소속 판정은 Custom Claims 로

```
request.auth.token.clinicId   소속 병원
request.auth.token.role       owner | manager | staff
```

**Firestore 문서를 읽어서 판정하지 않습니다.** Rules 안의 `get()` 은 호출마다
과금되고 느립니다. 품목 200 개를 그리면 판정이 200 번 일어납니다.

**대가**: 클레임은 **최대 1 시간 묵을 수 있습니다.**
소속이 바뀌는 모든 지점에서 `getIdToken(true)` 로 강제 갱신해야 합니다 —
그 일을 `public/auth.js` 의 `refreshClaims()` 한 곳에 모아 뒀습니다.

### 3-3. 진실은 하나 — 클레임

클레임과 Firestore 문서가 어긋나면 어느 쪽이 맞는지 알 수 없게 됩니다. 규칙을 정합니다.

> **클레임이 정답이고, `users/{uid}` 와 `clinics/*/members/*` 는 그 사본입니다.**

그래서 그 두 문서는 **Rules 에서 클라이언트 쓰기를 전부 막았습니다.**
`setClaims()` 는 항상 **클레임 → 문서** 순서로 씁니다. 중간에 죽으면 문서가
낡은 채 남는데, 반대(문서는 새것인데 권한이 없는 상태)보다 안전합니다.

### 3-4. 검증

`tests/rules.test.js` **33 건**. 눈으로 읽어서는 알 수 없어서, 남의 병원에
실제로 접근해 보고 거부되는 것을 확인합니다.

```
npm test        # 에뮬레이터를 자동으로 띄웠다 내립니다
```

**Rules 를 고칠 때마다 이 테스트를 돌려야 합니다.** 여기가 무너지면 제품이 끝납니다.

## 4. 입출고 원장은 고쳐 쓰지 않는다

`movements` 는 **create 만 되고 update · delete 는 아무도 못 합니다** (owner 포함).
잘못 넣었으면 **반대 전표**를 넣습니다.

원장을 수정할 수 있으면 재고 숫자의 근거가 사라집니다. "왜 이 숫자지?"에
답할 수 없는 재고 앱은 쓸모가 없습니다.

그리고 **원장 기록과 재고 갱신은 한 트랜잭션**입니다 (`repo.js` 의 `postMovement`).
따로 쓰면 중간에 끊겼을 때 재고와 이력이 어긋납니다 —
루미가 `currentStock` 과 `locations` 로 겪은 일입니다 (`ISSUES.md` FIXED-2).

## 5. 원가 — 이동가중평균

`RESEARCH.md` §A-7 / `DECISIONS-3.md` §3-1 에서 확정했습니다.

```
newAvg = (기존재고 × 기존평균 + 입고수량 × 입고단가) / (기존재고 + 입고수량)
```

`avgCostBase`(평균)와 `lastPriceBase`(마지막 매입가)를 **둘 다** 유지합니다.
발주할 때 보는 것은 평균이 아니라 마지막 가격입니다.

> 루미는 최종매입가를 덮어쓰는 방식이라 원가로 쓸 수 없었습니다 (`RESEARCH.md` §A).
> 그 값은 이관할 때 `lastPriceBase` 로 **이름을 바꿔** 넣고, 평균은 새로 쌓습니다.

## 6. 프런트엔드 — 빌드 없음, vanilla JS

루미와 같은 선택입니다. `BRIEF.md` 작업 규칙(바닐라 JS + Firebase SDK)을 따릅니다.

- 빌드 단계가 없으면 배포가 파일 복사입니다. 1 인 개발에서 이게 큽니다.
- 단, **루미의 실수는 반복하지 않습니다.** `staff.html` 은 18,000 줄짜리 단일
  파일이 되었습니다. 재고닥은 처음부터 **파일을 나눕니다** — `repo.js` / `auth.js`
  / 화면별 파일. 한 파일이 1,500 줄을 넘으면 그때 쪼갭니다.
